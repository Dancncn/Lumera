# 《源河》技术架构文档

## 概述

《源河》是一款 2–4 人的网页多人卡牌博弈游戏:UNO 式的牌面与出牌结构,叠加骗子酒馆式的「盖牌宣称 + 可撒谎 + 被质疑」博弈。美术与命名是架空西方古典风,内核是一套「源—四力—回流」的东方哲理设定,具体世界观与规则数值见独立文档。

本文档只覆盖技术架构:整体设计原则、技术栈、工程结构、引擎与协议的形态,以及分两阶段的实施路线。游戏的具体规则数值与平衡,刻意被隔离在引擎内部和一份可调配置里,既不在本文档展开,也不影响这里的任何架构决策。

实施分两阶段,顺序是先单机、后联机。阶段一做人机单机,完整实现游戏引擎和 AI 对手,全部在本地(浏览器内 WASM 或进程内)运行,不涉及任何网络。阶段二做联机多人,在同一套引擎外面套一层 WebSocket 传输,服务器只做消息分发。这个顺序之所以成立,是因为下面第一节的原则——引擎的接口本身就是网络协议,两个阶段共用同一套东西,不存在重写。

## 一、核心架构原则

整套系统建立在两条原则上,后面所有决策都从这里推出来。

**服务器权威(server-authoritative)。** 因为游戏的核心乐趣是盖着牌撒谎,真实牌面绝对不能存在于客户端。所有真相——每人的真实手牌、桌上盖着的牌究竟是什么、洗牌顺序、那一次掷的结果——只存在于权威的那一份引擎状态里。每个参与者(人或 AI)只能拿到一份过滤后的视图:自己的手牌、公开信息、以及别人嘴上宣称了什么。客户端永远不做规则判定,只渲染状态、发送操作。

**引擎即协议。** 游戏逻辑被收进一个纯粹的引擎,它对外只有两个动作:吃进一条命令(谁、做了什么),吐出一串事件加一份给每个座位的过滤视图。这个「命令进、事件出」的接口本身就是消息协议——单机时它走进程内的函数调用,联机时它走 WebSocket、序列化成 JSON。同一套 Command / Event / View 定义服务两个阶段,永不分叉。

由这两条推出的关键结论:AI 拿到的视图和真人完全一样,所以 AI 在结构上不可能作弊(它根本看不到底牌);也不存在「为单机和联机各写一套逻辑」的问题——引擎写一次,既编译成原生给服务器用,又编译成 WASM 给浏览器用。

## 二、技术栈

后端用 Rust。游戏引擎选 Rust 是因为这套隐藏信息状态机必须绝对可靠,而 Rust 的 enum 加 match 几乎是为状态机和「宣称牌 vs 真实牌」这类带数据的变体量身做的,编译器会逼你处理掉每个分支。网络层用 axum(基于 Tokio)。

并发模型是每个房间一个 Tokio task,task 独占自己的游戏状态,外界要改就往它的 mpsc channel 发消息,由它串行处理。这样几乎不需要 `Arc<Mutex>` 和锁——靠发消息而不是加锁来改状态,正是 Rust 里做并发最顺的一种写法,也天然没有数据竞争。

前端用 React 加 Vite 加 TypeScript。状态管理用 Zustand,轻、样板少,贴合「服务器推新状态 → 替换 store → 自动重渲染」这个数据流。动画上,大部分效果(翻牌、转盘)本质是 CSS 3D transform 就够,复杂编排可选 Motion(原 Framer Motion);要留意 React 在「整份状态被替换」的场景里容易踩 stale closure,需要稍加注意。

WASM 用来把引擎加 AI 编译成 WebAssembly(wasm-bindgen / wasm-pack),支撑阶段一的浏览器内单机对战;联机阶段也能顺手做客户端预校验,本地即时灰掉非法出牌,但权威判定永远在服务器。

序列化与类型同步:命令和事件枚举用 serde 加 `#[serde(tag = "type")]`,转成 JSON 就是天然的带类型字段消息;再用 ts-rs 从 Rust 类型直接生成对应的 TypeScript 类型,前后端协议永不对不上。

部署上 Rust 编译成单个二进制,用 rust-embed 把构建好的前端打进去,上线就是一个文件、一个进程。目标机器是广州那台 4C8G,对这种回合制、低频(大部分时间在等人出牌)的小游戏绰绰有余,单实例开几千个房间都无压力。

数据方面阶段一无持久化;阶段二房间状态先放内存,不上数据库,但留两个口子以备将来横向扩展(见第六节末尾)。

## 三、工程结构

一个 Cargo workspace,加一个前端目录:

```
yuanhe/
├── crates/
│   ├── engine/          纯逻辑:Game、Command、Event、PlayerView、规则、状态机、AI
│   │                    无 tokio、无 IO、无网络;可编译成原生 + WASM
│   ├── server/          axum + tokio:WebSocket、房间 task、消息分发(阶段二)
│   └── wasm/            wasm-bindgen 封装,把 engine 暴露给浏览器(阶段一)
├── web/                 React + Vite + TS 前端
│   ├── src/
│   └── package.json
├── scripts/             Windows 批处理:启动、构建
└── Cargo.toml           workspace 根
```

核心纪律:所有游戏逻辑只活在 `engine` 里,且 `engine` 不依赖 tokio、不碰 IO。`server` 和 `wasm` 都只是它的两层薄封装——一个把命令从 WebSocket 喂进去,一个把命令从 JS 喂进去。这是「引擎即协议、写一次跑两端」能成立的工程前提,也是必须守住的边界:任何规则判定一旦泄进 `server` 或前端,这个架构就破了。

## 四、引擎设计

引擎的核心是一个持有全部真相的状态机:

```rust
struct Game { /* 真相:各人手牌、牌库、桌上盖着的真实牌、命数/凝聚、计分区、受罚累进、当前 phase */ }

impl Game {
    fn apply(&mut self, seat: SeatId, cmd: Command) -> Result<Vec<Event>, GameError>;
    fn view_for(&self, seat: SeatId) -> PlayerView;
}
```

`apply` 先校验这条命令对当前 phase 和这个座位是否合法(只有当前玩家能出牌,只有下一家能质疑,只有受罚方能选点数),然后改状态、产出事件。`view_for` 把真相投影成某个座位有权看到的部分。

引擎是确定性的,唯一的随机(洗牌、受罚那一次掷)来自一个注入的、可种子化的 RNG,不在引擎里直接调系统随机。好处有三:测试可复现、AI 调试可复现、联机时随机完全由服务器掌控不下放;附带还让引擎能干净地编译进 WASM(因为它不向系统要熵,种子由调用方给)。

`view_for` 是整个系统的安全边界:它是 AI 和联机客户端拿数据的唯一入口,两者拿到的是同一个 `PlayerView`,因此「会读底牌的作弊 AI」在结构上根本写不出来。

## 五、状态机与消息协议

一个回合的循环如下(失败与出局的措辞已按世界观换皮,见第七节):

```
Setup ──发牌、定首家──┐
                      ▼
            ┌──────────────────┐
        ┌──►│   AwaitingPlay   │ ← 当前玩家
        │   └──────────────────┘
        │     │ 盖牌出数字牌 + 宣称 (PlayCard);功能牌明牌打
        │     ▼
        │   ┌──────────────────┐
        │   │ AwaitingChallenge│ ← 下一家
        │   └──────────────────┘
        │     ├─ Accept ────────► 出牌成立(手牌空则计分 + 补牌)→ 下一家 ─┐
        │     └─ Challenge(色|数)─► 亮真实牌、比对被质疑那一项 → 判输家     │
        │           ▼                                                       │
        │     ┌──────────────┐                                            │
        │     │  Punishment  │ ← 输家:选点、掷一次                        │
        │     └──────────────┘                                            │
        │       ├─ 中 → 一缕念被收回源头(扣凝聚)→(归零?→出局;全员?→结束)
        │       └─ 未中 → 摸牌、下次累进 +1                                │
        │         └ 梯子重启、定新首家 ────────────────────────────────────┤
        └──────────────────────────────────────────────────────────────────┘

牌库摸空 / 全员复归 ──► GameOver(按计分高低判胜)
两局之间:命运之轮转一次,定下一局首家(待定,见第七、八节)
```

命令(参与者 → 引擎):

```rust
#[serde(tag = "type")]
enum Command {
    PlayCard { card_id: CardId, claim: Claim },
    PlayFunctional { card_id: CardId },
    Accept,
    Challenge { target: ChallengeTarget },
    ChooseNumbers { numbers: Vec<u8> },
}
```

`PlayCard` 是盖牌出一张数字牌并宣称它是什么——撒谎就是 `card_id` 指向的真实牌与 `claim` 不一致;`PlayFunctional` 是明牌打功能牌;`Accept` 是放过、不质疑;`Challenge` 指定质疑上家宣称的颜色还是数字;`ChooseNumbers` 是受罚时选定要赌的点数。

事件(引擎 → 参与者,按可见性分发)包括:`TurnStarted`、`CardPlayed`(只播宣称、不播真实牌)、`FunctionalPlayed`、`PlayAccepted`、`Challenged` / `CardRevealed` / `ChallengeResolved`、`PenaltyPending` / `PenaltyRolled`、`Returned`(对应原「扣命/中枪」)、`CardsDrawn`(数量公开、真实牌只进当事人的视图)、`ChipScored`、`PlayerOut`(对应原「死亡」)、`LadderRestarted`、`WheelSpun`、`GameOver`、`Error`。

视图是每个座位拿到的过滤快照。公开部分有各人命数/凝聚、手牌数量(注意是数量、不是内容)、计分区、当前梯顶(宣称的那张牌)、出牌方向、牌库剩余、各人累进次数;私有部分只有你自己的真实手牌;桌上盖着的真实牌不在任何人的视图里,只有被质疑时才在 `CardRevealed` 中亮出。所有这些类型经 ts-rs 同步给前端,React 端拿到的是同名 TypeScript 类型。

## 六、可调参数

游戏平衡相关的数值全部抽进一个配置,与状态机隔离,调平衡时不碰任何逻辑:

```rust
struct GameConfig {
    starting_hand: u8,
    starting_lives: u8,
    chip_value: i32,
    return_penalty: i32,
    escalation_resets_on_hit: bool,
    refill_to_full: bool,
}
```

字段含义依次是:起手张数、初始命数/凝聚、每枚计分筹码分值、一次复归的扣分、累进次数是否在中枪后重置、手牌打空时是补满还是只摸固定张数。这一层存在的全部意义,就是让你反复调奖罚和概率时永远不必动状态机。

## 七、世界观接入

引擎和事件命名跟随《源河》设定,避免出现「死亡 / 枪 / 子弹」这类与世界观冲突的词。输不是死,是一缕念没汇成、被收回源头复归;惩罚那一下不是中枪,是源涌起把你这股淤水淹没。所以事件叫 `Returned` 和 `PlayerOut`(复归)而不是 `LifeLost` 和 `Death`,命数对玩家可呈现为「凝聚度」。机制完全不变,只换 Event 的命名与前端叙事。

命运之轮是一个只在两局之间转的 2D 转盘,用来定下一局的首家。先手在 UNO 里是实打实的优势,所以它有分量;它不碰任何牌、不改任何规则,纯靠那段「指针越转越慢、眼看要停又溜过一格」的悬念给情绪。它在状态机里对应 `WheelSpun` 与随后的首家选择。它是否最终采用、以及和「一梯结束后谁起新梯」如何统一,属于待定事项。

## 八、未定事项

以下是仍在讨论、尚未拍板的玩法决策。它们都被隔离在引擎内部与第六节的配置里,不影响本文档的任何架构决策,但需要在阶段一动手写引擎规则之前定下来。

1. 功能牌与万能牌的完整行为。反转和禁止已明确;万能牌被质疑时恒为真已定;但 +2/+4 作为计分筹码与作为「源之泛滥」出牌这两种说法,跨文档还没统一,需要确认它们到底是不是可打出的牌。
2. 一梯结束后由谁起新梯——质疑判定之后,以及有人打出 0(当 10、封顶)之后。这和命运之轮是否用来定先手是同一个问题,一次定了两边都清。
3. 手牌打空且未被抓时的补牌规则:补满到起手张数,还是只摸固定张数。注意补牌摸空牌库,正好就是游戏结束的触发条件之一。
4. 失败基调是「不甘的循环」(渴望落空、下把再来,张力强)还是「放下的复归」(汇成与否皆可,偏禅)。这个会渗进全部文案措辞,越早定越好。

## 九、本地开发(Windows)

用 Chocolatey 装工具链:

```
choco install rustup.install nodejs -y
cargo install wasm-pack
```

scripts 目录下放两个批处理。开发时分别启动后端和前端,Vite 把 `/ws` 代理到后端。

`scripts\dev-server.bat`:

```bat
@echo off
chcp 65001 >nul
cargo run -p server
```

`scripts\dev-web.bat`:

```bat
@echo off
chcp 65001 >nul
cd web
npm run dev
```

阶段一不需要后端:直接 `wasm-pack build crates/wasm` 产出 WASM 包给 web 引用,跑 `dev-web.bat` 就能在浏览器里玩人机。阶段二再起 `dev-server.bat`。上线时用 Cargo 把前端构建产物经 rust-embed 打进 server 二进制,部署到广州那台机器,就是单文件运行。

## 附:将来横向扩展的两个口子

阶段一二都用单实例加内存房间,这对你的规模是最优解,不要过早上 Redis。但为了将来真要放大时不必重写,现在就守住两点:其一,房间的存取藏在一个 `RoomStore` 接口后面(当前实现是内存里的 map),将来换成 Redis 存状态加 pub/sub 广播时,改动只集中在这一层,游戏逻辑一行不动;其二,每条 WebSocket 消息都自包含,带上 roomID 和玩家身份 token,不依赖「这条连接一直连在同一台机器」的隐含假设,这样将来加负载均衡、按房间路由都不难。这两点在小规模阶段的代码量跟纯内存版几乎一样,却把天花板抬高了。
